Généraliser : ce que le TP nous a appris

Dans le TP, vous avez suivi une requête vers un site. Ce cours court montre que ce que vous avez observé n'est pas un cas particulier : c'est le modèle qui fait fonctionner tout l'informatique en réseau.

Première Bac Pro CIEL Durée : 30 min Après le TP « Le voyage d'une requête web »
01

De l'exemple au modèle

Généralisation

Dans le TP, vous avez observé ceci :

flowchart LR A[Navigateur
le client] -->|requête HTTP| B[Site web
le serveur] B -->|réponse : HTML| A

Mais ce schéma ne décrit pas que le web. Il décrit toute communication en réseau :

Service Le client est… Le serveur est… Ce qui circule
Web (HTTP) Le navigateur Le serveur web Pages HTML, images, CSS
Messagerie Votre application mail Le serveur de mails Des messages
Jeux en ligne Le jeu sur votre PC ou console Le serveur de jeu Positions, actions des joueurs
Partage de fichiers L'explorateur de fichiers Le serveur de fichiers (NAS) Des documents
Impression Vos applications Le serveur d'impression Des travaux d'impression
À retenir n°1

Client-serveur n'est pas une notion « du web » : c'est le modèle universel des services en réseau. Un client demande, un serveur écoute et répond. Toujours.

02

Protocoles et ports : la langue et la porte

Vocabulaire

Dans le TP, vous avez relevé un port (443) et un protocole (HTTPS). Généralisons :

  • Un protocole est la langue commune : les règles précises de l'échange. Sans protocole partagé, pas de dialogue (comme deux personnes qui ne parlent pas la même langue).
  • Un port est la porte numérotée par laquelle le service écoute sur la machine. Une machine peut héberger plusieurs services, chacun sur son port.
Port Service Protocole
80 Serveur web HTTP
443 Serveur web sécurisé HTTPS (HTTP + TLS)
53 Serveur DNS DNS
25 Envoi de mails SMTP
22 Administration à distance SSH
À retenir n°2

Adresse IP + port = l'adresse complète d'un service (pas seulement d'une machine). C'est pour cela que le ping peut réussir alors que le site ne répond pas : la machine est joignable, mais la porte 443 est fermée.

03

Quand ça ne marche pas : une méthode, pas de la chance

Diagnostic

Les codes de statut du TP (200, 404, 403…) ne concernent pas que le web : toute application réseau renvoie des réponses structurées qui disent ce qui s'est passé. Un bon technicien lit la réponse au lieu de deviner.

flowchart TD P[Le service ne répond pas] --> Q1{La machine est-elle joignable ? ping} Q1 -->|Non| R1[Réseau, câblage, IP, machine éteinte] Q1 -->|Oui| Q2{Le service écoute-t-il sur son port ?} Q2 -->|Non| R2[Service arrêté, port bloqué, pare-feu] Q2 -->|Oui| Q3{La ressource existe-t-elle ? code de statut} Q3 -->|404| R3[Mauvaise adresse, fichier absent] Q3 -->|403| R4[Droits d'accès insuffisants] Q3 -->|200| R5[Le problème est ailleurs : côté client]

La démarche de diagnostic : de la machine vers le service, du plus large au plus précis — toujours dans le même ordre.

À retenir n°3

On ne teste jamais au hasard. On pose les questions dans l'ordre : machine joignable → service en écoute → ressource disponible. Chaque réponse élimine une cause.

04

Les 5 phrases à savoir dire

Synthèse
  1. « Le web est un service qui circule sur internet, l'infrastructure mondiale de réseaux. »
  2. « Tout service en réseau suit le modèle client-serveur : le client demande, le serveur écoute et répond. »
  3. « Un service est identifié par adresse IP + port ; le DNS traduit le nom de domaine en IP avant le dialogue. »
  4. « Le dialogue respecte un protocole (HTTP pour le web) ; les réponses portent des codes de statut qui disent ce qui s'est passé. »
  5. « Pour diagnostiquer, je teste dans l'ordre : machine joignable → service en écoute → ressource disponible. »
Et maintenant ?

Séance 2 : vous quittez le rôle de client. Vous allez installer le serveur sur votre propre poste — et revivre tout ce modèle… de l'autre côté du dialogue.
